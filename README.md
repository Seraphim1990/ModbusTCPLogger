Асинхронний логер телеметрії Modbus TCP, концентратор даних та REST/WebSocket API шлюз, розроблений для систем IIoT, промислової автоматизації та інтеграції зі SCADA. Створений на **Rust**

## 🏗 Архітектура та структура коду

Програма побудована під управлінням рантайму `tokio`. Окремі модулі спілкуються через типізовані асинхронні `mpsc`-канали.

### Центральний маршрутизатор повідомлень (`/messages`)
Усі підсистеми не залежать одна від одної напряму та маршрутизують свої операції через центральну шину подій за допомогою єдиного типу повідомлень `MainMsg` (`main_msg.rs`):

1. **`Request`**: Одноразовий запит (Oneshot pipeline). Ендпоінти REST API надсилають запит разом із каналом зворотного зв'язку `oneshot::channel`. Маршрутизатор перенаправляє запит до бази даних або оперативного кешу, який обробляє його та відповідає напряму в HTTP-хендлер.
2. **`Command`**: Команди модифікації (наприклад, додавання Modbus-пристрою чи регістру). Після успішної верифікації та збереження в MySQL, маршрутизатор надсилає сигнал `ConfigEventType` для сповіщення воркерів опитування.
3. **`Event`**: Події реального часу (статус опитування, втрата зв'язку з пристроєм, скидання TCP-контексту). Ці події транслюються в реальному часі на підключені WebSocket-клієнти та логуються на диск.
4. **`ConfigEventType`**: Сигнал гарячого оновлення конфігурації. При зміні налаштувань обладнання маршрутизатор адресує конкретні актори опитування, примушуючи їх перечитати конфігурацію "на льоту" без зупинки сусідніх потоків чи перезапуску всієї програми.

## Ключові можливості та модулі системи

### 1. Адаптивна система опитування Modbus (`/reader` та `/modbus_device`)
- **`node_master`**: Головний актор управління нодами опитування. Отримує сигнали від маршрутизатора бази даних і динамічно створює нові задачі опитування або передає сигнали до існуючих.
- **`node_loop`**: Актор-менеджер конкретної лінії (`reader_loop/read_loop.rs`). Керує життєвим циклом `ReadMaster`, контролює таймаути та приймає сигнали на оновлення воркера або видалення таску.
- **`ReadMaster` (`reader_loop/read_master_struct.rs`)**: Ядро опитування на базі `tokio-modbus`.
  - **Планувальник за принципом "найбільш відстаючого"**: Опитування проводиться в першу чергу для пристроїв з найменшим поточним timestamp.
  - **Адаптивний таймаут та самовідновлення**: Автоматично обробляє проблемні лінії зв'язку та помилки кадрів `HeaderMismatch` у `tokio-modbus`. При виникненні помилки таймаут пристрою динамічно збільшується на **+50 мс** (в базу даних не зберігається!) і виконується примусове скидання TCP-контексту для відновлення коректного стану Modbus-з'єднання. Така система гарно себе показала - кількість таймаутів впала на порядок.
  - **Оновлення конфігурації**: Перечитує конфігурацію пристроїв з БД за `oneshot`-запитом без зупинки роботи сервісу. Щоправда, при цьому скидається поточна черга опитування — це свідомий компроміс заради простоти реалізації.
- **Плагіни розшифровки (`/decoding_plugins`)**: Швидкі enum-базовані конвертери даних (`plugin_loader.rs`, `value_interface.rs`) із підтримкою зсуву коми (`ComaShift`), маскування біта в слові (`BitInWord`). Можна додавати свої плагіни, оскільки деякі розробники роблять власні методи розшифрування. `SatecDoubleRegistersInt32` яскравий цьому приклад. В абсолютній більшості випадків достатньо і перших двох. Енум вибраний був через складність `dyn Trait`. З мінусів потрібно перекомпіляція проекту, але це робить дуже рідко.

### 2. Розумне збереження телеметрії та кешування (`/db`)
- **Автоматична ініціалізація (`states.rs`, `db_init`)**: Автоматично створює структуру баз даних, необхідні таблиці та дефолтного адміністратора при першому запуску. Конфігурація підключення зберігається в зашифрованому вигляді у `configs/db.toml`. Програмі потрібен тільки логін та пароль для СУБД, все інше вона зробить сама і створить першого адміністратора.
- **Асинхронний маршрутизатор БД (`worker/db_master.rs`)**: Обробляє запити від API та спавнить таски для роботи з БД. Відповідь іде через `oneshot`-канали. Таски екрановані таймаутами. Для значень існує окремий під-таск.
- **Дедуплікація та кешування (`/hasher`)**: Керується актором `HashMaster` (`hash_master.rs`) та модулем `ValueHasher`:
  - **Дедуплікація**: Зупиняє запис однакових значень у базу (надсилає heartbeat-запис 1 раз на 5 хвилин, якщо значення стабільне). При обриві зв'язку чекає 2 хвилини і фіксує статус втрати даних без спаму в БД.
  - **Оперативний кільцевий буфер**: Зберігає до **131,072 записів на кожен тег** в оперативній пам'яті (~22 доби історії при 15-секундному опитуванні). Запити на побудову графіків та звітів віддаються миттєво з RAM, звертаючись до MySQL (`db_measure_unit.rs`) лише при виході за межі часового буфера. Розмір буфера можна міняти тільки перед компіляцією.
  - **Пакетний запис (`db_measure_unit.rs`)**: Об'єднує виміри у пакетні SQL-запити (Batch Insert size ≥ 20) для збереження ресурсу накопичувача та високої швидкості запису.

### 3. Розділення прав доступу та логічні угрупування
- **Фізична та логічна ієрархія**:
  - **Фізичний рівень**: Modbus-перетворювачі (`node_router`) -> Пристрої (`devices_router`) -> Регістри (`values_router`).
  - **Логічний рівень**: Цехи / Дільниці (`user_group_router`) -> Агрегати / Пристрої (`user_subgroup_router`). Прив'язуються через `assign_router`, що дозволяє формувати зручні операторські пульти. Буває, що лінія ModbusRTU іде через декілька цехів, і вам потрібно розділити пристрої логічно. Підгрупи тримають у собі значення. Якщо пристрій відповідає за декілька дільниць, або декілька пристроїв належать одній, їх можна згрупувати за значеннями.
- **Рольова модель (RBAC) (`auth`)**: Підтримує рівні `Admin`, `SuperUser`, `User` та `Service` із JWT-аутентифікацією (15 хв Access / 30 днів Refresh токени).
- **Real-Time WebSockets (`live_router`)**: Транслює поточні значення тегів та статуси обладнання. Автоматично розриває з'єднання кожні 15 хвилин для оновлення токену. Заодно сприяє вирішенню проблеми "повислих" сокетів. Дані ідуть за підпискою.

### 4. Захист ноди та прив'язка до заліза (`/minimal_copy_safe`)
- **Базовий ліцензійний захист**: При старті програма перевіряє configs/license.key на відповідність ідентифікатору локального накопичувача Windows. У разі неможливості отримати ідентифікатор перевірка не блокує запуск програми.

### 5. Система файлового логування (`/logger`)
- **Неблокуючий запис логів**: Щоб не створювати конкурентних блокувань бази даних при високому навантаженні, логи програми пишуться асинхронно у файлову систему.
- **Структуроване збереження**: Логи впорядковані за хронологією в директорії `logs/`, розділені по папках місяців та щоденних файлах (`logs/YYYY-MM/DD.log`).
## 🛠 Стек технологій

- **Ядро**: Rust, асинхронний рантайм `tokio`
- **Мережа та Web**: `axum`, `WebSocket`, `jsonwebtoken`, `tower-http`
- **Промислові протоколи**: `tokio-modbus`
- **База даних**: MySQL (sqlx)
- **Безпека**: JWT (JSON Web Tokens), прив'язка ліцензії до Hardware ID

##Швидкий старт

### Встановлення та запуск

**1. Клонувати репозиторій**

```bash
git clone https://github.com/Seraphim1990/ModbusTCPLogger.git
cd ModbusTCPLogger
```

**2. Підготовка бази даних**

Створіть базу даних та користувача в MySQL (або надайте root-доступ для автоматичного створення під час першого запуску).

**3. Запуск програми**

```bash
cargo run --release
```

При першому запуску програма запитає дані підключення до СУБД, згенерує `configs/db.toml`, створить структуру таблиць та перевірить локальний файл ліцензії.

Конфігурація `configs/server.toml` відповідає за налаштування сервера. UI надається через браузер.
